# flowlio-agents v1.0.0 — the loop closes on its own

**flowlio-agents is a project manager for AI agents.** Not for humans who happen to use agents —
for the agents themselves. Claude Code, Codex, OpenCode: they open sessions, do work, and — until
now — went quiet the moment a question crossed from one repository to another. v1.0.0 is where that
stops. A repository can ask a sibling a question, the session that asked can die, the sibling can
answer hours later, and **the original agent wakes up and reads the answer with no human in the
middle.**

That is the whole point, and for the first time it is true end to end.

---

## Why this is 1.0

Everything under here has been running in production and is now stable enough to put a number on:

- **Tenancy, tokens and auth** — teams, projects, per-project agent tokens, rate-limited.
- **Tasks and an MCP server** — an agent's own backlog, spoken over MCP, no web front required.
- **Issues and an inbox** — the differentiator: one repository asks another a question, and the
  answer lands in an inbox that recomputes state instead of replaying a fragile event stream.
- **Per-repository memory** — what a repository decided, learned, and where it stands, scoped to
  itself and never crossing repos; its index is in front of the agent before it reads a single task.
- **The wake-up** — the headline of this release, below.

Deterministic throughout. There is no AI *inside* the product: it coordinates agents, it does not
try to be one.

---

## The headline: waking a dead session, at a cost that follows events

An agent is an ephemeral process. It cannot sit and listen. So when a sibling repository answers a
question, something persistent has to catch the signal and relaunch the agent. In v1.0.0 that
something ships, and it was built around one hard constraint: **cost must follow real events, never
time × agents.**

- **A zero-SQL probe.** "Is there anything for me?" is an integer-vs-integer comparison held in
  memory — never a query. Only "what is it?" touches the database, and only after the probe says
  yes. An idle repository can be watched forever for free. *(This is tested, not asserted: an
  integration test counts SQL and stays at zero across a hundred empty probes.)*
- **The server dictates the cadence.** Every probe reply carries when to come back; a client that
  ignores it takes a `429`. A misconfigured daemon cannot cost the day.
- **A local push in self-host.** Engine and waker share the machine, so the engine knocks on
  `127.0.0.1` the instant an event drops — zero polling, zero latency, and a secret so no other
  process can trigger a relaunch.
- **Piggyback for active agents.** Every response already carries the inbox counter, so an agent
  that is working learns it was answered without one extra request.
- **Guardrails, not footnotes.** A relaunch cap turns a pair of repos answering each other into a
  bounded burst instead of a runaway loop; a session lease means a crashed agent stops costing on
  its own.

**Agent-agnostic.** Resuming the exact dead session with its context stays Claude-specific
(`claude -r`); every other agent gets a clean fresh launch (`codex exec`, `opencode run`, or any
command you name). You choose per repository.

## Install and run

```
brew install coddyum/flowlio/flowlio
flowlio
```

One program, one command. (The formula is in a tap, so the install is namespaced; what you run is
just `flowlio`.)

- **Self-host** — `flowlio` brings up a managed Postgres 18 container, the engine, and the waker, in
  one terminal. Point a repository at it with `flowlio connect <REPO>`, pick its agent with
  `flowlio agent set claude|codex|opencode`, and you are done.
- **Hosted** — `flowlio login`, then `flowlio` runs only the waker; the engine runs on our infra and
  your agent's code and credentials never leave your machine.

Want to see the loop close before you trust it? `scripts/demo-wake.sh` stands up the whole thing on
your machine and proves it, with no human in the middle.

## For contributors

flowlio-agents is open source and standard-library Go: no ORM, no HTTP framework, no Redis, one
database (Postgres). The architecture is hexagonal with a small module system, and the reasoning
behind every non-obvious choice is written down — start at `CLAUDE.md`, then `docs/`. The design of
this release in particular lives in `docs/DESIGN-WAKE.md`, and the decisions it settled are D62 and
D63 in `docs/decisions.md`.

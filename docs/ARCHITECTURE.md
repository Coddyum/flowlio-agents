# ARCHITECTURE — flowlio-agents

Map of the domains and of the inter-module interfaces. To be read before editing an unfamiliar
area, to be updated as soon as a feature or an inter-module interface appears.

## Current state

**M1, M2 and M3 shipped**: tenancy and agent tokens; tasks and stdio MCP server; cross-project
issues and state inbox.

Design decisions: [DESIGN-V1.md](DESIGN-V1.md) for the v1 scope, [DESIGN-M3.md](DESIGN-M3.md) for
the model of the issues and of the event journal — to be read before touching `issue`, `inbox` or
`events`, it explains choices that look surprising for as long as the reason is missing (notably:
the cursor only drives a display flag, never the presence of a row).

## Routing

The engine mounts every module under `/api/<Key()>/` and strips the prefix
(`http.StripPrefix`): a module declares its routes relative to itself (`POST /x`,
`DELETE /x/{id}`).

Global middleware (engine, applied to every route, in order): `Recover`, `Logger`. A feature's
middleware (auth…) is bound once in its `module.go`.

**CORS** (`engine.CORS`) wraps the router, applied in `main.go` and not in the engine's default
chain: the origin list is configuration (`ALLOWED_ORIGINS`), and the engine takes none. It is the
outermost, which is necessary — a browser preflight carries no token, so it must be settled before
the auth middleware.

It serves **one** caller, the self-hosted web screen calling this API from the browser, and it is
the only cross-origin door in the product. An operated deployment allows no origin at all
(`ALLOWED_ORIGINS=,`) and the middleware is inert there. What must be true before it is deleted is
written at the top of `internal/core/engine/cors.go`; on 2026-08-07 none of it was.

> **These are the only response headers this server sets on its own.** There is no
> `X-Content-Type-Options`, no `X-Frame-Options`, no HSTS, no CSP, no `Referrer-Policy` anywhere in
> the repository — the global chain is `Recover`, `Logger`, and that is all. Stated here so nobody
> reads the CORS middleware as "the security headers" and believes removing it would cost only
> CORS: there is nothing else to lose, and nothing else to keep.

| Rule | Why |
| ----- | -------- |
| Never `*` | this API answers to an administration token that lives on the user's machine |
| Strict equality on the origin | `https://flowlio.me.evil.test` passes any substring test |
| No `Allow-Credentials` | there is no cookie in this product; the token leaves in `Authorization` |
| `Vary: Origin` always set | otherwise a cache serves one origin the headers computed for another |
| A request without an `Origin` untouched | the CLI and the MCP server are not browsers |

## Domains (features)

| Module key  | Domain                            | Routes                                                                                                            | Inter-module dependencies |
| ----------- | --------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------- |
| `workspace` | teams, projects, agent tokens      | `/api/workspace`: `POST/GET /teams`, `POST/GET /projects`, `POST/GET /tokens`, `DELETE /tokens/{id}`, `GET /whoami` | none                      |
| `task`      | a project's backlog + notes        | `/api/task`: `POST/GET /`, `GET/PATCH /{number}` — **one single write route**: note and archiving are fields of the PATCH | none                      |
| `issue`     | cross-project questions + thread   | `/api/issue`: `POST/GET /`, `GET /{project}/{number}`, `POST /{project}/{number}/answer`                            | none                      |
| `inbox`     | actionable state of the project    | `/api/inbox`: `GET /`                                                                                               | none                      |
| `overview`  | team-scoped read, supervision      | `/api/overview`: `GET /`, `GET /refs/{project}/{number}` — **read-only, no write at all**                            | none                      |
| `ref`       | resolution of a CORE-34 reference  | `/api/ref`: `GET /{project}/{number}` — **read-only, owns no table**                                                | `task` and `issue`, through the `FeatureRegistry` |

`workspace` scopes: the administration routes require an `admin` token (`AdminOnly`);
`GET /projects` and `GET /whoami` accept any valid token and stay scoped to its team. An admin
token designates the targeted team through `?team=<slug>`; a project token cannot leave its own,
even by forcing the parameter.

`task` scopes: **every** route requires a token of `project` scope (`requireProjectScope`, bound
once in `module.go`). A backlog is the internal work of a repo: no route takes a project as a
parameter, so there is no surface where a scope could be bypassed. An admin token, bound to no
project, gets a `403`.

`team_id` **and** `project_id` appear in every query of `sql/queries/tasks.sql` — including the
insertion of a note, fed by a `SELECT` scoped on the task. The isolation between projects of one
same team is covered by `internal/feature/task/store/store_integration_test.go`.

**Dependencies between tasks** (`task_dependencies`, `sql/queries/dependencies.sql`): an edge says
"A is blocked by B until B reaches S". When B reaches it — or is archived, since it will then never
reach anything again — the edge is released, a `task.unblocked` is journalled on the UNBLOCKED
task, and that task goes back to `todo` **if and only if** all its edges are lifted and at least
one of them was blocking it (`set_blocked`). Those three conditions live in the `ClearTaskBlock`
query, inseparable, so that no caller can forget one. All of it is written inside the transaction
of the patch that triggers it: outside a transaction, the state "the blocker is `done`, the blocked
task does not know" would become reachable again.

**Two surfaces open an edge, and each owns what it opened** (D47). `block_task` / `unblock_task`
are the nominal path for an agent. The other is a line in a description, compiled at write time:

```
#blocked-by @CORE-34 until #done
```

One `@`, one `until`, alone on its line, outside any code fence. A line **detected but unreadable
refuses the entire write**, description included — ignoring it would make a typo indistinguishable
from a task carrying no dependency. What is compiled is the **diff** between the stored body and
the one being written: a line appearing opens the edge, a line disappearing releases it — and only
if a line had opened it. The `origin` column carries that ownership, so no description edit ever
lifts a block an agent decided (`service/blocked_by.go`, `service/blocked_by_sync.go`).

**An edge never crosses a repo** (D42), and it is not the service that guarantees it: the table's
two composite foreign keys share the same `project_id` column, so a cross-project dependency is
**inexpressible**, not merely refused. Proven without going through the service in
`store/dependency_integration_test.go`. The cross-repo need already has its object: the issue. A
cycle is refused at write time by a Go walk of the project's active graph (`service/cycle.go`) — a
pure function, hence provable without a database.

`overview` scopes: **both routes require an `admin` token** (`AdminOnly`, bound once in
`module.go`). There is no mixed gate, and none must be introduced: it is the only surface of the
product that reads a WHOLE team, including the thread of a conversation between two repos the
caller is neither the author nor the recipient of. Under `auth.Middleware`, an agent would read the
questions of its sibling repos, and the isolation tests of `task` and `issue` would stay green.

The team always comes from the server-side resolution of `?team=<slug>`: no UUID enters or leaves
this surface. An admin carrying a team is locked into it — the same guard as `workspace`, and it is
written in both places because a defence that lives in another file is not a defence.

`ref` scopes: **a token of `project` scope is required**, like every surface an agent uses. An
admin token is refused rather than made to designate a target: a reference is read FROM a project,
and a principal that has none has nowhere to read from.

This module owns no table and writes nothing. It keeps **one** query (`sql/queries/ref.sql`) for
the single fact neither of its two peers can give it: the key of its own project. That is what
tells `CORE-34` — mine, hence possibly a task — apart from `FRNT-34`, a sibling's, hence
necessarily an issue. Without that guard, the task query, scoped on the token's project, **would
find** something: the caller's task 34, yielded under a reference that names somebody else.

## Inter-module interfaces

**One single composition exists, and it is `ref`** (FLWL-16, settled on 2026-08-05). A project's
counter is shared between tasks and issues: an agent reading `CORE-34` does not know which of the
two it is. `ref` answers the question in one HTTP request, where the MCP layer made two — on the
path `check_inbox` feeds, hence the most called of the product.

| Interface | Declared in | Implemented by | Consumed by |
| --- | --- | --- | --- |
| `module.TaskRefResolver` | `internal/core/module/module.go` | `task` (`provider.go`) | `ref` |
| `module.IssueRefResolver` | `internal/core/module/module.go` | `issue` (`provider.go`) | `ref` |

Three choices of shape, each with a reason that cannot be guessed:

| Choice | Why |
| --- | --- |
| The interfaces live in `internal/core/module` | provider and consumer must name the **same** type for the registry's type-assert to succeed, and a feature does not import a feature: this package is the only one all three already share |
| The payload is raw JSON (`json.RawMessage`) | what a resolver yields is the API view of the owning feature; naming `taskservice.TaskDetail` here would drag a feature into the core. `encoding/json` copies a `RawMessage` as such, so the cost is nil |
| Two interfaces rather than one | their signatures look alike; a single one would let `ref` question the wrong module and still compile, on a path whose entire business is telling a task apart from an issue |

`ref` is a **pure consumer**: it registers itself under no useful key, and it must not — offering
the composition to the features it composes would open a cycle that would only show at run time.
It carries **no write at all**, for the same reason: mutating somebody else's domain from a module
that has no query to carry the scope would have no guardrail.

On the other hand, **several features share tables** — that is not an import, so
`check-cross-feature-imports.sh` does not see it, and that is why it is written here. `overview` is
the extreme and the cleanest case: it reads seven tables, six of which are not its own, and writes
none (decision M3 #26 — reading another domain's table through a dedicated scoped query is
allowed, writing to it is not).

| Table      | Owner          | Other writers / readers                                                  |
| ---------- | -------------- | ------------------------------------------------------------------------ |
| `projects` | `workspace`    | `task` and `issue` in **write** (`ClaimNextNumber`), `inbox`, `overview` and `ref` in read |
| `tasks`    | `task`         | `inbox` and `overview` in read (bucket of tasks in progress)             |
| `issues`   | `issue`        | `inbox` and `overview` in read (incoming and outgoing buckets)           |
| `events`   | `issue`        | `inbox` in read                                                           |
| `teams`    | `workspace`    | `overview` in read (resolution of the slug into a scope)                 |
| `tokens`   | `workspace`    | `auth` in read/write (`last_used_at`), `overview` in read (a repo's pulse) |
| `issue_messages` | `issue`  | `overview` in read — **the only simple FK of the lot**, hence the only one where the team clause really bears |
| `task_notes` | `task`       | `overview` in read (`last_move`, and the detail of a task)               |

The rule that makes this sharing safe: **every query carries its tenancy scope**, whichever feature
writes it. A shared query taking a bare identifier would be a hole for every feature at once, not
only for its own.

### The repository's two scoping rules

Since `overview`, "carrying its scope" no longer means one single thing. The repository counts
**two**, and a re-reading that confuses them lets through exactly the hole it was looking for.

| | Rule A — project | Rule B — team |
| --- | --- | --- |
| Predicate | `team_id = @team_id AND project_id = @project_id` | `team_id = @team_id` **alone** |
| Where | `tasks.sql`, `dependencies.sql`, `issues.sql`, `inbox.sql`, `ref.sql`, `trust.sql`, and the project-token queries of `tokens.sql` | `overview.sql` |
| Meaning of the `team_id` | comes from the principal (`Principal.TeamID`) | comes from a **server-side resolution** of the `?team=` slug (`OverviewTeamBySlug`), never from a client UUID |
| Write | allowed | **forbidden** — read-only, checked by `scripts/check-overview-scope.sh` in `make lint` |
| Gate | `requireProjectScope` | `AdminOnly` |
| Exposed over MCP | yes | **no** — an agent reading the state of its team destroys the isolation promise |

The two rules do not sit next to each other in one same query file: a team-only query and a
project-scoped query over the same tables is the setup where copy-paste leaks (decision M3 #24).
Every file carries its rule at the top, so a reader opening `overview.sql` without context
understands the absence of `project_id` without opening another file.

**Two files fall under neither rule, and that is deliberate:**

| File | What it carries | Why it is not rule B |
| --- | --- | --- |
| `projects.sql` | `team_id` alone, **without `AdminOnly`** | It is the team directory, readable by a project token: metadata only (key, name), settled in [DESIGN-V1](DESIGN-V1.md) § Isolation. Should it be filtered further? Open question, card FLWL-44. |
| `teams.sql` | **no tenancy predicate at all** | `GET /teams` enumerates every team of the installation. Of no consequence in `local` mode — one human, one admin token. **The day is here**: an operated instance holds one team per paying customer, so the route is reachable only by the operator's admin token and must never be published to a customer-facing surface. Blocking for M7, item 2 of card FLWL-9. |

Writing a query in either of these two files therefore requires knowing which of the four
situations is being reproduced. That is precisely the reason for this table.

What that is worth, measured and not asserted: `internal/feature/matrix_integration_test.go`
(`TestScopeRouteMatrix`) mounts the six modules on their real stores and covers three principals —
project, admin, none — against the six route prefixes. A `requireProjectScope` that accepted
`|| p.IsAdmin()`, or an `AdminOnly` that accepted a project scope, makes a cell fall over.

Locking constraint not to be broken: `ClaimNextNumber` must never write a key column. For as long
as that holds, Postgres takes a `FOR NO KEY UPDATE`, compatible with the `FOR KEY SHARE` the
insertion of an issue lays on its two parent projects — otherwise two symmetric agents (FRNT→CORE
and CORE→FRNT) deadlock each other. Detail in [DESIGN-M3.md](DESIGN-M3.md).

Reminder of the pattern, as `ref` really exercises it: `main.go` registers every module under its
key, the consumer resolves **lazily** (`registry.Get("task")`) and type-asserts on the interface
declared in `internal/core/module`. The resolution happens at request time and **never in
`NewModule`**: every module is built before the first one is registered, so a peer captured at
construction time would always be nil. No `internal/feature/<other>` import — checked by
`scripts/check-cross-feature-imports.sh` (hook + `make lint`).

A peer missing from the registry is a **wiring failure**, never a "not found": yielding a 404 would
make a badly mounted instance look like an empty backlog.

Every new inter-module interface is documented here **and** validated with the human.

## Shared services (`CoreServices`)

`Auth()` only. `Billing()` will come with the hosted mode (M7). A feature-specific service never
enters `CoreServices`.

## Transactions

The store exposes a `Transactor` (`WithTx(ctx, func(Store) error) error`). `*sql.DB` never leaks
into the service: the service sees nothing but the store interface. Implemented in `task` and
`issue`; `inbox` has none, because all it does is read a state.

**Nesting is refused, not absorbed.** A `WithTx` inside a `WithTx` would open a second transaction
on another connection of the pool, which would wait on the lock the first holds on the project's
row — a deadlock no single-threaded test reveals. Silently joining the transaction in progress
would be worse: the outer one would commit the writes of an inner call whose error had been
swallowed.
